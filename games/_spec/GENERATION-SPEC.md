# 文字密室关卡生成规范（阶段3）

本文件是所有关卡生成任务的唯一规格来源。生成器可以参考 `reference/game.json`（样板关）的写法，但内容必须原创，禁止照搬样板的套路（停摆挂钟报时密码、北极星编号按钮等已列入禁用元素）。

## 一、game.json 数据格式

```json
{
  "title":  "关卡标题（页面大标题）",
  "intro":  "开场引子，1-2句，交代处境与目标（可选）",
  "start":  "起始房间ID",
  "rooms":  { "房间ID": { "n": "房间名", "d": "房间描述（≤80字）" } },
  "items":  { "物品ID": "物品名" },
  "puzzles": [ { "id": "谜题中文名", "solved": "解开后置位的标志", "clue": "线索标志" } ],
  "acts":   [ { ...动作... } ],
  "difficulty": { "minSteps": 10, "maxSteps": 28, "maxBranch": 6 }
}
```

动作（act）字段：
| 字段 | 说明 |
|---|---|
| `id` | 英文蛇形，全局唯一 |
| `room` | 动作所在的房间ID |
| `label` | 玩家看到的动作文字（按钮），像玩家会说的话 |
| `req` | 可用前提 `{ "i": ["物品"], "f": ["标志"] }`（两组是 AND） |
| `n` | 排除前提 `["标志"]`：标志已置位时动作隐藏 |
| `eff` | 效果 `{ "i": ["获得物品"], "rm": ["移除物品"], "f": ["置位标志"] }` |
| `go` | 移动到目标房间（可与 eff 并存） |
| `end` | `"win"` 或 `"lose"`（终结态） |
| `text` | 执行后的结果文案；纯移动类可不写 |

引擎语义：状态 = 房间 + 物品集 + 标志集。动作可见 = 在 `room` 且 `req` 全满足且 `n` 全不满足。执行 = 应用 `eff`，再跳 `go`，`end` 终结游戏。

## 二、验证器七项检查（node tools/validate.js <game.json>，退出码 0 = 全过）

1. **结构完整**：引用的房间/物品必须存在；动作 ID 唯一；全关标志并集 ≤ 20。
2. **可通关**：存在到达 `end:"win"` 的路径。
3. **无死局与软锁**：每个可达的非终结状态都必须仍能通关。
4. **无孤儿内容**：每个动作必须在某个可达状态里出现过；每个物品必须能获得；每个房间必须可达。
5. **线索先于谜题**：每个谜题必须存在"已获 clue、未获 solved、未结束"的可达状态；`puzzles` 必须声明且非空。
6. **解法唯一**：`eff.f` 含 `p.solved` 的动作必须恰好一个。
7. **难度区间**：最短步数 ∈ [minSteps, maxSteps] 且平均分支 ≤ maxBranch。

## 三、防软锁守则（照做即可通过检查3）

- 所有移动**成对可逆**（A→B 与 B→A 都写动作），除非剧情上是终结走向。
- `eff.rm`（移除物品）只允许出现在 `end:"lose"` 的终结动作里。
- `n` 只允许两种用法：
  (a) 错答动作写 `n:["该谜题solved标志"]`——谜题解开后错答自动消失；
  (b) 自隐藏的一次性动作：`n:[X]` 且自己的 `eff.f` 里也有同一个 X。
- 禁止用 `n` 隐藏移动动作或任何通关必需动作。
- 标志一旦置位不可撤销，规划依赖时保证"先拿到再锁门"不成立。

## 四、设计约束

- 房间 6–10 个、谜题 5–8 个，以种子难度带的指引为准；标志 ≤20（命名建议 `c_` 前缀线索、`p_`/语义命名解法与门）。
- 标志预算技巧：谜题 `solved` 标志直接兼作门/通道标志（`req.f` 引用它），省出预算。
- 种子的两种机制都必须落实为具体谜题（每种至少 1 个），并在 concept.md 里写明哪个谜题对应哪种机制。
- 错答选项每谜题 ≤3 个；每房间可见动作峰值控制在 7 个以内（保平均分支 ≤6）。
- 房间描述 ≤80 字；**句式必须多样**（不要每间都是"A。B，C。"三段式），禁止跨房间复用同一句子。
- 失败/错答文案要有变化（"锁纹丝不动""没有反应"这类不许复用超过一次）。
- 文本里禁止 HTML、尖括号、引号嵌套陷阱；动作 label 简短具体（≤14字为宜）。
- 最短路径可能跳过线索动作（密码可被乱试解开）——这是允许的，但胜利最终动作必须有物品/标志依赖，避免一步通关。
- `end:"lose"` 最多 1 个（可选），必须是玩家可识别的危险动作。

## 五、产出流程（顺序执行）

1. `games/<id>/concept.md`：设定（场景、氛围、处境与目标，2-4 段）、谜题清单（表格：谜题 | 对应机制 | 线索在哪 | 解法动作 | 解开后效果）、结局（win/lose 文案方向）。
2. `games/<id>/depgraph.md`：依赖图表格：谜题 | 需要的线索(来源动作) | 需要的物品(来源) | 前置谜题 | 解锁什么。末尾写明"环检查：无环，通过"。
3. `games/<id>/game.json`。
4. `node tools/validate.js games/<id>/game.json`：非 0 按报错修改后重跑，**最多 5 轮**；5 轮仍失败 → 把 games/<id>/ 移到 `rejected/<id>/` 并在 `rejected/<id>/REASON.md` 写明每轮报错与失败原因。
5. 通过后 `node build.js games/<id>/game.json games/<id>/index.html`。
6. `games/<id>/gen-notes.md`：记录每轮 validate 的报错与改动、最终指标（states/shortest/avgBranch）、自查清单结果（房间数/谜题数/标志数/80字检查/句式多样性）。

## 六、边界（禁止触碰）

- 只允许写 `games/<id>/` 下的文件（以及按流程写 `rejected/<id>/`）。
- 引擎 `engine/play.html`、`tools/validate.js`、`build.js`、`reference/`、`seeds.json`、样板 `escape-sample.html`、根目录 `game.json` 一律只读。
- 不运行试玩（阶段4负责），不写 INDEX.json（主控负责）。

## 七、补充澄清（试点 g01 后修订，与前文同等效力）

- **clue 标志的置位来源必须早于解法动作可达**：允许由前一谜题的解法动作或其它前置动作顺带置位，但不允许某谜题的 clue 只能由它自己的解法动作置位（否则"线索先于谜题"必挂）。多个谜题可共用同一 clue 标志，但设计上不要超过一处共用。
- **指标口径**：seeds.json 里的 targetShortest 是参考目标，验证器硬带（minSteps/maxSteps/maxBranch）才是硬约束；两者冲突时保机制完整度，偏差如实记入 gen-notes。
- **分支计数口径**：氛围动作（≤2/房）与错答动作（≤3/谜）都常驻计入平均分支；两者叠加后仍受"每房可见动作峰值 ≤7"约束。平均分支无法事前精确估算，以验证器输出为准。
- **移动动作 label** 允许在不同房间同文（如多个"回大厅"）；"句式不复用"约束的是描述与反馈文本。
- **"同一问题连续 3 次失败"** 指同一验证器检查项（如"无死局与软锁"）因同一设计缺陷连续 3 轮修不过；不同检查项的失败分别计数。
- **事务性标志**（领取物品/读取资料类动作自隐藏所需的一次性标志，如 `ash_dug`）计入标志预算，规划时预留 1-3 个。
- **通行动作（带 go 的动作）一律禁用 `n`**：实测证明"解谜后隐藏入口"类写法会造成离开后无法重返的软锁。门禁请用 `req.f` 持续放行（解谜标志一旦置位即长期满足）。
- **clue 引用另一谜题的 solved 标志**：允许，不算"共用"；"共用不超过一处"仅指两个谜题声明同一个 clue 标志。一个动作顺带置多个线索标志不受此约束。
- **"每房可见动作峰值 ≤7"** 计入 lose 终局动作与成对回程移动；超限时优先折叠氛围动作。
- **`end:"win"` 的动作**若对应 puzzles 里声明的终局谜题（solved 如 `won`），必须同时 `eff.f` 置位该 solved 标志（否则"解法唯一"报错）。
- easy 关容差明确为"最短步数 ≤ 参考目标上限 +2"。
- **错答动作的 `n` 只挂本谜题的 solved 标志**（第49行规则的强化）；若需要随其它前置消失，把该前置并进错答的 `req` 而不是再加 `n`。
- **解法泄密判据（评审实测定稿）**：解法动作 label 不得含唯一正确配置/结果。密码拨号类用"枚举候选"（≥2 候选动作，错答纯 text、复用既有标志）；配平排序类用中性 label＋错档错序反馈；口诀/映射/配方必须两源合成（一处残缺、一处补全），任何单块牌/贴纸不得完整给出口诀。
- **共用 clue 的口径**：每个 clue 标志最多同时作为两个谜题的声明线索，且其中一个应为弱依赖；被其它谜题的解法动作引用不算共用。一个动作顺带置多个线索标志建议 ≤3 个。
- **首个谜题的 clue 惯用模式**：先写一个前置感知动作（读登记本/听广播/查看封条等）顺带置位首个 clue，避免"线索只能由自己的解法动作置位"的死角。
- **认知谜题可加 req 强制读线索**：解法动作允许且建议 req 引用线索标志（尤其 hard 关），保证推理链不可被乱试跳过；错答动作同理。
- lose 动作不算氛围动作，只计入每房峰值。
- **氛围动作**（无 eff 的纯文本动作）每房 ≤2 个——它们会常驻计入平均分支。
- **布局与步数带的优先级**：步数带优先于房间数。medium 关建议 7-8 房的紧凑拓扑；hard 关可用 8-10 房但要注意 maxSteps 36 的上限。若两者冲突，先压缩移动开销（合并枢纽房间、减少回头路）。
- **生成前必读 `games/_spec/banned.md`**，禁用元素一个都不许出现。
- `games/g01/` 是已通过的成品示例，可参考其文档结构与文字质量基准，但句子、桥段、文案一律不得复用。
- 同一问题（同一报错/同一设计缺陷）连续 3 次修复失败 → 不再重试，把该种子移入 `rejected/<id>/` 写明原因，继续下一个。
- 文字原创性：不许与其它关卡共享任何整句；错答、开场、结局文案必须为该关独立撰写。
